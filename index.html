NIDS complete team of 4

Network Intrusion Detection System

A machine-learning IDS trained on CICIDS2017 that sorts network flows into 15 classes (DDoS, brute force, botnet, benign and more), with SHAP explanations so every flagged flow shows why it was flagged.

Stack
Python · scikit-learn · XGBoost · SHAP · pandas · Dash / Plotly · Tshark
Performance
Random Forest weighted F1 99.77% · MCC 0.992 · macro F1 0.85weighted F1 is carried by benign traffic; macro F1 counts every attack class equally. Random split; cross-day evaluation is next.
What I built
  • Benchmarked Random Forest, XGBoost and SVM on weighted F1 and MCC.
  • Handled extreme class imbalance with SMOTE, fitted on the training split only.
  • Per-flow SHAP attributions shown alongside each detection.
  • Near-real-time monitoring dashboard with live packet capture.
Errata
A 99.77% score deserves suspicion. The split and SMOTE are leak-free, but XSS detection sits at F1 0.27 and SQL injection has 4 test samples. The headline number is mostly benign traffic being easy. Cross-day numbers will be lower and more honest.

FIRE building role: temporal / weather models · team of 6

FireGuard — Wildfire Spread Forecasting

Next-day wildfire spread prediction on WildfireSpreadTS: satellite, terrain and weather rasters for 607 fire events (2018–2021). The prototype replays historical forecasts; live next-day forecasting is being built into the final product.

Stack
Python · PyTorch · U-Net · GeoTIFF rasters · GFS / GRIDMET weather
What I built
  • Own the temporal and weather side: how multi-day weather enters the spatial model.
  • Audited the weather channels against raw rasters before trusting them, then wrote the temporal input contract the rest of the team builds on.
  • Integrated every role's branch into one working prototype.
Errata
The weather data looked fine until I checked it against the raw files: the GFS wind-direction channel only spans −90° to +90° (half the compass), and GFS precipitation isn't consistent across years. Both now have to be handled explicitly before they reach a model.

MEAL v1.0.0 role: architect / design lead · QA · team of 4

MealSync — Mess Management

Replaces a university mess's paper meal cards, registers, Excel sheets and "show me your payment screenshot" checks with one system for students, counter staff, the mess office and the committee.

Stack
Node.js · Express · MySQL 8 · JWT / bcrypt · Jest + Supertest · GitHub Actions · OpenAPI
Measured
128 tests · 95.5% line coverage · CI on SQLite and MySQL 8
What I built
  • A signed QR pass that rotates every 30 seconds, so screenshots expire and passes can't be shared.
  • Server-verified payments (HMAC signature) instead of trusting payment screenshots.
  • One plate per student per meal enforced by the database; every refused scan is logged as a fraud signal.
  • Skip-a-meal credits and a live veg / non-veg headcount for the kitchen.
  • 19-table schema in 3NF, layered routes → controllers → services, full SRS / UML / test documentation.
Errata
The interesting bugs weren't in the code but in the mess's rules: what counts as "late", when a skipped meal earns credit, who may cancel mid-month. Every rule ended up as an editable setting.

GIVE complete with Tarun Das · team of 2

GiveGrid — Donation Matching

Connects donors with verified NGOs: donors list usable goods, NGOs post needs, the platform ranks matches and runs the workflow from claim to handover. One donation can be split across several NGOs.

Stack
HTML / CSS / JS · Node.js · Express · MySQL 8 · bcrypt · JWT · Jest + Supertest · Postman
Measured
120 tests · 92% line coverage · 10,272 seeded rows, every measured request in milliseconds
What I built
  • Race-safe claims with SELECT … FOR UPDATE: two NGOs claiming 70 of 100 chairs at the same instant, exactly one wins.
  • A claim changes four rows in one transaction, all or nothing.
  • Append-only donation history enforced by MySQL itself, not by convention.
  • 48-hour holds that a timer releases exactly once if no pickup is confirmed.
Errata
Our first concurrency test sent requests one after another and passed against broken code. Removing the lock now makes 5 of 9 concurrency tests fail, so the tests actually detect the race.

CYCL building AI & soft computing course · team

Cyclone Response with Fuzzy Logic

Disaster-management decision support for North Indian Ocean cyclones in three stages: forecast wind 24 hours ahead, score the threat, then turn threat into a resource-allocation priority. Replayed on Fani, Amphan, Biparjoy, Mocha and Remal.

Stack
Python · NumPy · pandas · Mamdani and Sugeno (TSK) inference · NOAA IBTrACS
Measured
v1 forecast test MAE 10.6 kt vs 12.9 kt persistence baselinelinear forecaster; the ANFIS stage is in progress
What I built
  • IBTrACS pipeline with train / validation / test split by storm, so no cyclone leaks across sets.
  • Mamdani threat score from wind speed and distance to land.
  • TSK priority score mapped to resource units through a declared policy table.

A fuzzy threat score should rise when wind rises. My own monotonicity check on v1 said it didn't always, so the system is being rebuilt as a clean input-to-prediction prototype.

XAI coprocessor — unit 1

Explanation Consistency as a Coherence Prior for Reliable Neural Decision-Making

Extended position paper · with faculty co-author · submitted to IJCNN 2026 · in revision for resubmission

Deep networks can be highly accurate and still fail silently. This paper proposes explanation consistency, whether a model's explanations stay stable under small input perturbations, as a reliability signal separate from predictive accuracy, evaluated on medical imaging datasets.

The core argument: a model can generalise from the wrong features and never be caught by accuracy metrics. Explanation stability surfaces exactly that gap.

finding: high-confidence predictions can have unstable explanations, exposing failure modes accuracy metrics never see. In safety-critical systems, that gap is the whole problem.

  • 4-stage, in-order
  • no speculative execution
  • no branch prediction either

How I Work

CTRL_UNIT

Every problem goes through the same four stages. No speculative execution: I don't ship what I can't explain.

  1. IF

    Fetch

    Read everything first: docs, source, raw data, packet captures. Raw input beats secondhand summaries.

  2. ID

    Decode

    Break it into parts small enough to trust. If it still seems too complex, it isn't decoded yet.

  3. EX

    Execute

    Build the smallest thing that proves the idea, then grow it. Working beats elegant-but-imaginary.

  4. WB

    Writeback

    Test it, document it, and be able to defend every line. A result only retires once it's explained.
